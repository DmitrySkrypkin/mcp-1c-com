# Архитектура mcp-1c-com

## Поток данных

1. MCP-клиент (Cursor) запускает `server.py` по stdio.
2. `FastMCP` регистрирует tools и принимает JSON-RPC вызовы.
3. `OneCConnection` лениво открывает `V83.COMConnector.Connect(...)`.
4. `execute_query` создаёт объект `Query`, выставляет параметры, читает выборку.
5. Значения COM сериализуются в JSON (даты → ISO, ссылки → UUID).

## Почему COM, а не расширение

HTTP-MCP в расширении требует хранения расширений в ИБ. На режиме совместимости конфигурации **8.2.x** платформа это запрещает. Внешнее соединение COM работает на уровне платформы и не зависит от возможности хранить `.cfe`.

## Потоки

Объекты COM 1С привязаны к apartment потока создания. Все вызовы к соединению идут под одним `RLock` в том же потоке, где соединение было открыто. MCP-запросы обрабатываются последовательно.

## Несколько информационных баз

Один процесс = одно соединение (набор `ONEC_*`). Для второй базы Cursor запускает второй процесс с другим `env` — отдельные имена в `mcpServers`.
